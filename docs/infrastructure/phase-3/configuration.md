## Inventory method

Existing names come only from `packages/tooling/src/env.ts`, `.env.example`,
`apps/web/.env.example`, `turbo.json`, `scripts/neon-targets.mjs`,
`.github/workflows/*.yml` and a name-only scan of scripts and source. No private
`.env` file was opened or printed. Inventory codes:

- **E**: existing application name in a schema or example.
- **O**: existing operator, test or CI name.
- **P**: provided by a platform.
- **N**: proposed name. N names are not implemented; each needs schema,
  redaction and consumer changes in its authorized phase.

Environment codes: L local, C disposable CI, S staging, P production. Every
secret has a different value in every environment where it exists.

**Stores.**

| Store | Meaning                                                                                                                                                                                                                                  |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RR    | Application Render workspace environment group, scoped to staging or production; protected and network-isolated (RDR-10).                                                                                                                |
| RC    | Separate Render organization/account and recovery-only Pro workspace; independent recovery-only logins/API tokens; separately scoped staging and production environment groups. No application-workspace identity can read these values. |
| RN    | Netlify project variable marked secret, Runtime or Functions scope only (NET-06); never a team-shared variable.                                                                                                                          |
| PUB   | Reviewed public configuration: provider setting, build variable or committed config.                                                                                                                                                     |
| OV    | Operator vault shared by P and B: password manager with MFA, recoverable by B without P's devices.                                                                                                                                       |
| VM    | Root-only files (mode 0600) on the parser host, provisioned from OV.                                                                                                                                                                     |
| GH    | GitHub Actions: ephemeral workflow token, or a protected environment for a future publish job.                                                                                                                                           |
| LD    | A developer's private `.env`; never committed, copied or bundled.                                                                                                                                                                        |

**Owner.** For every row, **P** (Shane Viyazhi) executes creation and rotation
and **B** (Sherise Viyazhi) holds independent recovery and revocation access
(P3-U03).

### Rotation policies

| Policy | Applies to                                                                          | Trigger and cadence                                                                                                    | Overlap and revocation                                                                                                                                                                                                                                                       | Audit and recovery                                                                                                           |
| ------ | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| R1     | Provider API keys and client secrets                                                | Immediately on suspected exposure, role change or provider advisory; reviewed monthly; rotated at least every 90 days. | Create a restricted replacement, deploy and verify it, then revoke the old key within 24 hours, or immediately on compromise even if requests fail. Resend keys are deleted, not rotated in place (RES-04).                                                                  | P logs key ID, scope and UTC times, never values. B can revoke and replace from OV.                                          |
| R2     | Signing secrets: auth, proxy, capabilities, recovery manifest and recovery receipts | Immediately on exposure; planned every 90 days.                                                                        | Key IDs where supported. Capabilities accept the previous key only for the longest issued lifetime. Changing Better Auth's single secret logs every user out, and integrity wins over seamlessness. Netlify and the API swap the proxy secret together in a recorded window. | P records the effect and time; B can force logout and rekey.                                                                 |
| R3     | Database credentials, including the export login                                    | Immediately on exposure or role change; quarterly.                                                                     | Reset one role at a time, redeploy consumers, drain old pools, verify role profile and RLS. Never grant extra privilege to keep a service running. Phase 4 writes the exact Neon procedure.                                                                                  | P records role, target and grant diff; B can reset through the Neon console and verify the target guards.                    |
| R4     | Public and policy configuration                                                     | On any domain, release or policy change; reviewed quarterly.                                                           | Versioned through reviewed changes; roll back only to a previously reviewed value; never widen auth origins silently.                                                                                                                                                        | P records the reviewed change; B restores the last known-good configuration.                                                 |
| R5     | Operator and infrastructure tokens, private CA keys, recovery-account logins        | Per task where possible; long-lived tokens reviewed monthly with a 90-day maximum; CA keys rotated on exposure.        | Short-lived and least-privilege. Revoked after the task or incident. Leaf certificates valid 90 days and renewed at 60; a CA change runs with dual trust until every leaf is replaced.                                                                                       | P records token IDs, scopes and certificate serials; B holds independent break-glass access to every provider and the vault. |

worker, scanner or parser.

## Leakage prevention and emergency revocation

Rules:

- **No secret in browser-visible or published artifacts:** no secret is a
  `NEXT_PUBLIC_*` or `VITE_*` value, a Docker build argument or image layer, a
  source map, a client DTO or a URL.
- **No secrets in output:** nothing prints environment dumps, connection
  strings, cookies, authorization headers, capability URLs, OAuth query
  strings, webhook raw bodies or document text. Errors carry stable codes,
  field names and a correlation ID; the existing schema loader already reports
  only field names.
- **Least exposure:** each process receives only the variables it needs.
  Pull-request workflows receive no secrets. The image check is extended in
  Phase 5 to fail on secret-looking environment defaults. Secret scanning
  stays enabled for this public repository.

On suspected exposure, the incident commander acts:

1. Contain: disable the affected route or feature, or suspend the service.
2. Revoke the credential at the provider.
3. Install a restricted replacement.
4. Invalidate dependent sessions and capabilities, and fence running jobs.
5. Reconcile uncertain provider operations (payments, AI, email) before any
   retry.
6. Verify, then record scope, UTC times, actor and affected artifact, never
   the value.

B can do all of this if P is unavailable. An exposed credential is never
restored from a backup.

## Transactional email design

Selected design P3-D17:

- **Sending identities.** Production sends from `notify.nthawi.io` and staging
  from `notify-staging.nthawi.io`. These are dedicated subdomains, so the
  apex reputation stays separate from any future mailbox (RES-01). Both use
  Resend region `eu-west-1`. Account data stays in the United States
  regardless of region (RES-02).
- **From.** Production `Nthawi <noreply@notify.nthawi.io>`; staging marks the
  sender and subject as staging.
- **Reply-To.** Must be an owner-approved, monitored mailbox. No monitored Reply-To mailbox is confirmed; the absence of apex MX (OBS-H02) does not establish whether an external mailbox or sender exists. Real email stays off
  until P names the mailbox and P and B accept its monitoring; no `support@`
  address is invented. Named support responsibility is already a gate before
  paid launch (v0.3).
- **Return-Path.** Choose Resend's default or a custom Return-Path subdomain
  when the domain is created (RES-01).
- **DNS records.** Copy the exact provider-issued verification, SPF and DKIM
  records, with their record types, into Cloudflare as DNS-only. No values are
  invented here.

**Keys and restrictions.** API and worker get separate sending keys, each
restricted to its environment's domain (RES-04). Staging enforces
`EMAIL_RECIPIENT_ALLOWLIST` in the adapter, so a staging key can only reach
synthetic recipients even though it is a real provider key.

**Sender inventory and DMARC.** Before adding records, inventory every
legitimate sender and every existing MX, SPF, DKIM and DMARC record; the
current inventory is empty (OBS-H02). Keep one valid SPF policy per name within
the lookup limit, and preserve unrelated selectors. Publish
`_dmarc.nthawi.io` at `p=none` with an aggregate-report destination P
approves. Confirm SPF or DKIM alignment on representative messages from both
subdomains, then stage to `quarantine` and later `reject` on evidence. The
subdomain policy (`sp`) effect is stated explicitly in that record.

**Webhooks.** `POST https://api.nthawi.io/api/v1/webhooks/resend` (proposed
path). The route verifies the Svix signature over raw bytes with `svix-id`,
`svix-timestamp` and `svix-signature` (RES-03), enforces a 5-minute timestamp
tolerance (a design value, because RES-03 states none) and rejects oversized or
malformed input. It persists the event ID and a minimal payload before
returning 2xx, then processes asynchronously, tolerating duplicates and
out-of-order delivery. Bounces and complaints update suppression and the
operator-visible delivery state. They never change payment, access or
financial records. After an uncertain send response, the worker reconciles by
provider message ID before retrying, using stable notice idempotency keys.

**Notices.** The approved v0.2 schedule is preserved exactly.

- Enqueue English notices within 5 minutes of: verified purchase and receipt,
  accepted cancellation, approved refund obligation, provider-confirmed
  refund or reversal, and completed purge.
- Reminders at term end minus 3 days and minus 1 day, at the expiry instant,
  1 day before grace ends, and 7 days before abandonment-purge eligibility.
- Obsolete notices are recomputed or cancelled when a grant or lifecycle
  generation changes.

Four states are kept distinct, and each is claimed only on its own evidence:
**queued** in the outbox, **accepted** by the provider (API response with
message ID), **delivered** to the recipient server (webhook) and **inbox
placement**, which is never claimed. Missing email never extends access or
proves a payment or refund. Phase 3 registers no domain, creates no key and
sends no email.
